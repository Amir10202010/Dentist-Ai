# Deployment

The application is a long-running ASGI server that holds patient imaging on
disk and talks to Postgres. That shape rules some hosts in and others out, and
the exclusions are worth stating first because they are not obvious.

## Why not Vercel

Vercel runs serverless functions, and three properties of this application are
incompatible with that model — not awkward, incompatible:

- **The filesystem is not persistent.** CBCT volumes are content-addressed
  blobs of tens to hundreds of megabytes, written under
  `DENTIST_AI__STORAGE__ROOT` and read back by public id. A serverless
  filesystem is per-invocation and empty, so an upload would succeed and the
  next request would 404.
- **Analysis outlives the request budget.** Decoding a volume and running the
  pipeline over a 112³ grid is a CPU-bound job measured in seconds to minutes.
  Function timeouts land in the middle of it.
- **It is not a static site with an API attached.** Pages are Jinja-rendered by
  the same process that serves the JSON, under `uvicorn` with two workers.

The same reasoning excludes Netlify and Cloudflare Pages. What is needed is a
container host with a persistent disk.

## Render (configured)

[`render.yaml`](../render.yaml) is a complete Blueprint: a Docker web service,
a managed Postgres 17 instance, a 10 GB disk, and a generated signing key.

1. Push to `main`.
2. In the Render dashboard: **New → Blueprint**, select this repository.
3. Confirm the plan. Render then builds `Dockerfile`, provisions the database,
   runs `alembic upgrade head` as a pre-deploy step, and redeploys on each
   push to `main`.

Nothing needs to be typed into the dashboard — `DENTIST_AI__SECRET_KEY` is
generated by Render, and `DENTIST_AI__DATABASE__URL` is injected from the
managed instance.

Cost is the one decision the Blueprint cannot make: the free instance type has
no persistent disk and sleeps when idle, so `plan: starter` is the floor. Both
the service and the database are billed.

### If the first deploy fails on a write under `/app/var`

The image runs as the non-root `dentist` user (uid 10001), and a disk mounted
root-owned leaves it unable to write. Add an init step to the service's
**Docker Command** in the dashboard, or mount the disk one level deeper at
`/app/var/storage` and let the image's own `mkdir` own the parent. This is the
only step that cannot be verified without an account, so check the first
deploy's logs rather than assuming it worked.

## Other container hosts

`render.yaml` is Render-specific, but nothing else is. The image is a plain
Dockerfile and the application is configured entirely through environment
variables, so Railway, Fly.io, a VPS running `docker-compose.yml`, or any
Kubernetes cluster will run it given:

| Variable | Required | Notes |
| --- | --- | --- |
| `DENTIST_AI__SECRET_KEY` | yes | ≥32 characters; the app refuses to boot in production without it. Generate with `python -c "import secrets; print(secrets.token_urlsafe(48))"`. |
| `DENTIST_AI__DATABASE__URL` | yes | `postgres://`, `postgresql://` and `postgresql+asyncpg://` are all accepted; the scheme is normalised and libpq's `sslmode` is translated for asyncpg. |
| `DENTIST_AI__ENVIRONMENT` | yes | `production` or `staging` — this is what turns on the secret-key check. |
| `DENTIST_AI__STORAGE__ROOT` | no | Defaults to `/app/var/storage` in the image. Must be a persistent volume. |
| `DENTIST_AI__ML__BACKEND` | no | `stub` by default. `yolo` additionally requires the image built with `--build-arg INSTALL_ML=1` and weights mounted at `DENTIST_AI__ML__WEIGHTS_PATH`. |

Run `alembic upgrade head` before starting the app; `docker-compose.yml` shows
the ordering as a `service_completed_successfully` dependency.

## Model weights

`models/best.pt` is deliberately not in the repository — committing a 52 MB
binary makes every clone download every past revision of it. The container
ships without weights and runs the stub detector. The CBCT pipeline is
unaffected: it is NumPy-only and has no learned weights to distribute.
